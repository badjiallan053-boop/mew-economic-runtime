# Accounting kernel specification

The kernel (src/core/mew.mjs, class MEW) prevents individually admissible agent actions from exceeding one principal's economic mandate when those actions are considered together. The decision path is deterministic JavaScript; no LLM approves spending.

An objective has a stable ID, principal, precommitted semantic key, integer quantity and integer maxExposure. An effect has an immutable ID, objective ID, semantic key, provider, type and integer amount. The principal supplies equivalence; this build does not infer it from text. A second objective with the same principal and semantic key is rejected. Different semantic keys are a trusted configuration boundary, not proof that goals differ.

All money is an integer count of one asset's minor units. An objective is denominated in a single `asset` (default `lovelace`); an effect in a different asset is DENIED. No currency conversion is performed. The canonical fixture permits one report and at most 1,000,000 units; Alpha costs 550,000 and Beta 490,000.

## Accounting and decisions

Spent is settled value. Reserved is authorized value that has not yet committed. Committed is verified in-flight value. Exposure is their sum; these categories are disjoint. Equivalent paid or unresolved effects consume objective capacity, even when delivery is unknown. Full verified refund or verified failure/release of an unpaid reservation can restore capacity. Delivery satisfaction and payment settlement are separate facts.

ALLOW reserves capacity before dispatch. DEFER means reconcile the original effect rather than issue another payment. DENY rejects mandate mismatch, exceeded budget, reused effect identity or completed objective. simulate uses a copy and does not reserve real capacity. Server persistence must wrap evaluate plus reservation write in one database transaction. A reservation has no automatic timeout release: silence does not prove a payment failed.

Claims have stable IDs, source, effect ID, type and evidence. Replay of identical evidence is idempotent; conflicting evidence is rejected. Payment settlement requires rail verification by a trusted rail source (`cardano`, `web2`; configurable per kernel instance via the `rails` option). The web2 adapter verifies an HMAC webhook signature over the raw body with a timestamp tolerance, then binds the event to the reservation's effect, principal, asset, amount and recipient. Claim ID replay is idempotent and conflicting evidence is rejected. The single shared `WEBHOOK_SECRET` means any holder can attest any effect; per-provider secrets and real tenant isolation are not implemented. A signed `payment.failed` event releases a still-reserved effect. The Cardano verifier reads transaction and output evidence from the fixed preprod Blockfrost origin, validates a 64-character hash, exactly matches recipient lovelace sum to the reserved contract, and requires latestHeight - transactionHeight + 1 to meet its threshold. It never signs or sends payments. Confirmation depth is a configured observation policy, not absolute finality.

## Threat model and prototype limits

The API boundary is trusted. A JSON field `evidence.verified=true` is not a signature or an oracle. Demo claims are controlled fixtures and must stay labeled simulation. Real payment claims must be produced server-side by a verifier; the server must prevent reuse of one transaction for multiple effects. The recipient and amount must come from the persisted reservation, not from a reconcile request. Merchant delivery remains a trusted input and requires authenticated signed receipt verification before production.

The accounting layer only governs actions sent through it. Bypassing MEW, malicious principals, forged upstream data, compromised Blockfrost credentials, chain rollback and multiple independently deployed reservation stores are outside this demo's guarantees. Production requires principal authentication, authorization per objective, signed mandates and receipts, resilient reconciliation, scoped secrets, durable backups and coordinated multi-instance locking. Public demo state must never control wallets. A test suite proves the checked scenarios, not every economic workflow.


## Evidence export

`buildEvidenceCase` (src/core/evidence.mjs) produces a versioned, purpose-bound case: mandate, operations with ledger-native status plus shared-vocabulary state, exposure by original asset, a digested timeline with source class (synthetic, authenticated, independently_observed, operator_attested), missingness and limitations. Terminal ledger states (failed, released, refunded) map to no shared state and are flagged for review; nothing maps directly to RESOLVED. The export carries no score and no underwriting conclusion.


## Local dispatch and assurance evaluation

`Store.enqueue` commits a kernel reservation and version-1 outbox row together with BEGIN IMMEDIATE. Existing databases retain their snapshot; legacy `/api/evaluate` continues to reserve without dispatch. A queued request is bound to the persisted effect, with canonical digest and stable submission key. The worker rechecks these terms and terminal state before claiming work. A transaction persists a monotonically increasing token and attempt before any provider call. Expired DISPATCHING becomes UNKNOWN; neither lease expiry nor a lookup outage releases capacity. Stale owners cannot record observations.

The worker accepts only the explicit `SandboxProvider` or `StripeSandboxProvider` and rejects shared/aliased runtime and receiver database files. This provider persists its own purchases/events. Matching request keys deduplicate; altered payloads fail. Reliable not-found permits bounded same-key retry; pending/unavailable or exhausted attempts remain UNKNOWN with an operator-review reason. The lease fences local writes, not external sends: durable receiver idempotency is essential. Simulator settlement/delivery/refund observations are synthetic, and the existing evidence schema never gains an inferred RESOLVED state. Late delivery and full undelivered refunds can be refreshed atomically; partial refunds and signed receipts are unsupported.

The runner starts clean database pairs for each frozen case/mode. The oracle grades accepted receiver records and events against the declared mandate independently of admission verdicts. It tracks original-asset cumulative charges, verified refunds, current commitment and transient peak. Four unsupported controls remain NOT_IMPLEMENTED. Independent outside-tool purchases produce an explicit bypass failure. The bounded report contains no prompts, headers or credentials; its canonical digest detects alteration but is not a signature or proof of truth. SQLite coordination applies to processes sharing one local store, not separate deployments or network filesystems.


The Stripe adapter is test-only and opt-in via a private CLI. It validates the configured account through the fixed API, whitelists USD cents and the test payment method, persists request identity before creation, and records only validated PaymentIntent references. Retrieval by that reference survives restart. Unknown creation responses replay the exact key within a conservative 22-hour window; after that, absence of a reference requires operator review. Missing local journal records never become authoritative not-found. Provider polling is asynchronous and outside MEW transactions. Test API success never implies merchant delivery, production settlement, signed mandates or live customer payment. Generic Web2 HMAC intake remains distinct from Stripe's signature format; the separate loopback sandbox receiver now verifies Stripe snapshot signatures, durably queues minimized events, and reconciles payment state using read-only API retrieval. Unknown creation can be recovered after the replay window only when a verified event supplies an exact PaymentIntent reference that the API binds to the persisted request.


`DeliveryVerifier` implements a local simulated exact-artifact protocol. Public Ed25519 supplier and owner keys plus criteria digest are immutably bound to the persisted operation before dispatch. A supplier receipt verifies actual artifact bytes; a separate owner signature is required for acceptance after settlement. Receipt alone never satisfies delivery. Receipt/acceptance replay is durable, conflicting evidence fails, and acceptance plus delivery claim commit atomically. Rejection retains paid exposure. The simple pilot uses generated fixture keys, not real enrollment or human review. Production identity, revocation and signed-receipt release gates remain pending; see docs/runbooks/DELIVERY_ACCEPTANCE.md.
