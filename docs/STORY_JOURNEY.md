# The MEW website story

Reviewed 7 October 2026 against local website source. This is a journey design and evaluation plan, not evidence of visitor conversion or customer demand. Ownership: the journey writer owns this document; the implementation lead owns shared navigation and interface changes.

## One audience, one recurring purchase

The first visitor is a team building agents that buy work. Its question is practical: if a supplier's response times out, can another agent accidentally buy the same deliverable? Follow one research report throughout the primary journey. The proposed clip workflow is a secondary application, not an unexplained change of customer job.

Use the studio's exact illustration: one report, 3 ADA maximum principal exposure, Alpha at 1.50 ADA and Beta at 1.40 ADA. Their sum is 2.90 ADA and fits the monetary ceiling. The one-report quantity is what prevents a second equivalent purchase while the first remains unresolved. Do not explain this example as a budget overflow. Fees are excluded; no wallet or payment is involved. The principal supplies equivalence before admission; MEW does not infer equivalent goals from natural language.

## Four visible steps

| Step | Visitor question | Observation or action | Next action | Evidence boundary |
| --- | --- | --- | --- | --- |
| Understand — home | Why would our team need this? | Inspect the timeout illustration: a first commitment remains counted when its outcome is unknown. | Try decision demo | Client illustration; synthetic values, not a paid operation. |
| Try — studio | What happens to the repeat purchase? | Start fresh, advance the timeout checkpoints and inspect the DEFER result and retained report capacity. Answer the learning check. | Verify the decision | Hosted persisted simulation; shared state can be reset by another presenter. |
| Verify — protocol evidence section | What does this prove? | Distinguish implementation boundaries, the hosted fixture result and pending live integrations. External sources support integration research separately. | Plan a bounded pilot | Tests cover checked cases; library sources do not prove customer demand or a payment occurred. |
| Plan — pilot | What could we validate with our workflow? | Prepare a local one-report brief with explicit acceptance and a recovery rule. Download it for review. | Review the draft with the team | Planning only: no submission, signup, booked supplier work or spending authorization. |

Navigation should name these steps consistently: Understand, Try, Verify, Plan. Indicate the active page accessibly. Secondary workflows, design tools, clip rehearsal and research sources stay reachable without competing with the next primary action. A case summary near the next-action panel keeps the same report, prices and outcome visible across pages.

## Corrections found in the source audit

1. Home used a 1 ADA / 0.55 ADA illustration while studio used 3 ADA / 1.50 ADA / 1.40 ADA. Align the homepage inputs, visual track, accessible labels and JavaScript checkpoint descriptions with the studio. Changing headings alone leaves contradictory live content.
2. Studio's evidence side panel and Pilot tab directed visitors to five clips. Replace the primary handoff with implementation verification and the one-report pilot brief. Keep clips as a clearly labelled secondary example.
3. Research is a collection of publisher observations and announcements. Its current content cannot substitute for implementation proof. The Verify page must separate code/test evidence from hosted fixture observation and proposed live proof.
4. Pilot download is the end of a local planning tool, not an application funnel. Explain the next human review and the absence of a connected booking channel beside the download outcome.
5. Avoid the absolute promise “No duplicate purchase” without a scope qualifier. Admission only governs actions passing through the configured MEW mandate and store; uncontrolled external purchases remain outside the guarantee.

## Suggested next-action language

- Home: “Try the timeout case” / “See why an unresolved report still holds capacity.”
- Studio: “Verify this decision” / “Inspect what the simulation shows and what still needs live proof.”
- Verification: “Plan your report pilot” / “Define acceptance, an agreed limit and a recovery rule before supplier work.”
- Pilot: “Download your review draft” / “Review this locally with your team. No application or purchase is submitted.”

These are proposed labels; implementation must use the actual controls and routes. Keep synthetic mode visible beside the result, rather than only in the footer.

## Review and learning plan

A successful first-value observation is that a visitor can explain why 2.90 ADA still does not permit a second equivalent report under the one-report mandate, locate supporting evidence and prepare a bounded draft. This remains a hypothesis until observed in customer sessions.

Review the complete journey at mobile and desktop widths, using keyboard only and reduced motion. Check the shared-case numbers, active navigation, next actions, actual DEFER checkpoint, learning feedback, draft download and browser refresh. Source inspection does not replace rendered verification. Do not report analytics, conversion, time savings or activated customers: none is established by this document.

## External references and limitations

- [Stripe's official one-time Checkout sample](https://github.com/stripe-samples/checkout-one-time-payments) documents a minimal educational example, shared client routes across server variants, local setup and optional webhook testing. The useful pattern is one concrete flow with explicit setup and verification. No Stripe implementation or payment claim is copied into MEW.
- [Vercel's official examples](https://github.com/vercel/examples) distinguishes solutions/reference demonstrations from functional starters and asks examples to document environment setup and a demo URL. MEW likewise needs an inspectable demonstration whose setup and limits remain clear. This is workflow reference, not product validation.
- [Salesforce's demo guidance](https://trailhead.salesforce.com/content/learn/modules/product-demos-quick-look/how-to-create-a-product-demo) was retrieved as a primary product-demo reference. MEW's customer problem and evidence remain governed by its own reviewed source.
- A focused YouTube demo tutorial candidate, [MS68CCaFP5Y](https://www.youtube.com/watch?v=MS68CCaFP5Y), was attempted; retrieval returned an internal error and no transcript was obtained. No knowledge or recommendations are attributed to unseen video content.

Skills applied: local jury UI/UX, narrative score and value proof. They provide review procedures, not independent deployment or customer evidence.

The artwork uses zero retained report capacity to show scope rather than a reservation, including rejected-recipient cases. The checkpoint-record link opens its disclosure.
